# LLVM text assets

## Reviewed formatting catalog

`templates.json` is the ordered source catalog of ASCII LLVM fragments.
`templates.bin` and `../src/LLVMTemplates.bas` are generated together; edit the
JSON and regenerate rather than editing their offsets or numeric IDs. Names
describe emitted operations and remain the API used by the emitter modules.

```powershell
rtk proxy powershell -NoProfile -File bootstrap/tools/llvm-templates.ps1 -Write
rtk proxy powershell -NoProfile -File bootstrap/tools/llvm-templates.ps1
```

The default command compares both generated outputs byte for byte. Generation
rejects duplicate/invalid names, unsupported characters and numeric placeholders
outside `{0}` through `{3}`. Other LLVM braces remain literal. Line endings are
normalized to CRLF; tab, CR and LF are admitted along with printable ASCII.
The catalog has at most 4,096 entries and a total size of 1 MiB; a fragment may
use that full size. Source-token string limits do not apply to this reviewed
compiler asset.

`LLVMTemplates.TrySpan(Id, Start, Count)` supplies a fragment's byte span.
`LLVMFormat.TryValidateCatalog` checks exact extent, admitted bytes and the
generated byte sum. This detects accidental corruption, not hostile substitution;
source parity requires the generator's full-byte comparison.
`TryFormat(State, Buffer, Token, Catalog, Template, P0, P1, P2, P3)` validates the
whole selected fragment before writing it, then uses `LLVMWriter` for spans and
exact signed LongLong decimal parameters. `TryLine` additionally writes one
CRLF. Callers choose whether a multiline fragment already contains its ending.
Catalog input and writer scratch buffer must be distinct arrays. Formatting
failure latches writer failure code 3 and cannot publish partial output.

The formatter gate checks every current catalog entry at O0/O2, including exact
bytes, repeated placeholders, literal braces, multiline text, signed extrema,
malformed catalogs and changed-input negative controls. This qualifies formatting,
not the semantics of all complete programs assembled from those fragments.

## Windows runtime source

`windows-runtime.ll` contains the fixed memory/array, counted-file, system-I/O, path, process and namespace support
definitions used by the Windows x64 target. It is 95,098 bytes of UTF-8 without
a BOM, with CRLF line endings (byte sum 7,669,073). The UBE emitter reads these actual bytes; it
must not extract support or procedure bodies from a previously emitted program.

Verify source parity before using this asset in acceptance gates:

```powershell
rtk proxy powershell -NoProfile -File bootstrap/tools/runtime-text.ps1
```

After reviewing an intentional bootstrap runtime change, regenerate with the
same command plus `-Write`, then rerun the check. The tool reads only
`EmitMemoryRuntime` in `bootstrap/src/SourceEmitter.bas` and the eight functions
called by `NativeFileIR` in `bootstrap/src/NativeFileRuntime.bas` and five
functions called by `NativeProcessIR` in `bootstrap/src/NativeProcessRuntime.bas`. It recognizes
their literal concatenation statements, doubled-quote escaping, `vbCrLf` and
the explicitly reviewed `CStr(MaximumArrayElements)` constant (1,048,576).
That constant must still match its unique public source declaration. Unknown
statements, expressions, interpolations or composition changes are errors.
No VB6 executable or host-generated program IR participates in extraction.
The bootstrap keeps its existing embedded text so its standalone executable
does not acquire an external-file dependency; the parity gate guards drift
between these two source representations during the UBE port.

## Shared private target ABI

Emit these types before the asset, with actual module and storage counts:

```llvm
%ube.resource = type { i64, ptr, ptr, i64, i64 }
%ube.context = type { i64, i64, [M x i64], [F x i64], ptr, i64, i64, [64 x %ube.resource] }
```

Context fields are Err number (0), call depth (1), module states (2), module
storage cells (3), leaf-block list (4), charged bytes (5), live blocks (6), and
resource registry (7). Resource fields are token, native handle, scratch-block pointer,
resource kind and busy flag. The asset itself defines `%ube.block` as next pointer,
reference count and charged bytes. Array descriptors remain four i64-sized
cells: lower bound, upper bound, payload pointer, owning-block pointer.
These are private lowering layouts, not public source or foreign layouts.

No replacement markers are needed: the complete asset is appended verbatim
after the context types. It contains the process-wide atomic resource token counter,
Windows import declarations, target wrappers, memory collection/allocation,
array replacement and file registry/transfer support. All runtime support calls
are resolved within the asset or by its declared Windows imports.

The consuming emitter must separately generate the target triple, checked
arithmetic intrinsic declarations, context size/init/dispose, project/module
initialization, validated primitive wrappers, source procedures and executable
entry. None of those project-specific definitions is copied into this asset.
Named `ube.target.allocate`, `ube.target.release` and `ube.target.file.*`
definitions remain narrow test fault-injection boundaries. The asset has no
test flags and contains no generated user procedures.

The source parity command passed after generation. This verifies textual parity,
not native execution or qualification of a new emitter; the native lowering
acceptance gates must establish that separately.

The current runtime is 95,098 bytes with byte sum 7,669,073; the 133-template
catalog is 22,016 bytes with byte sum 1,727,128. Run runtime-text.ps1,
llvm-templates.ps1 and native-imports.ps1 without -Write to verify source parity.
The import definition contains exactly 41 reviewed Kernel32 imports.
