# Native failure-flow feasibility gate

This is a hand-authored LLVM target experiment for the owner-approved
[error contract](../../../lang-doc/error-handling.md). It establishes that
ordinary native calls and branches can implement the selected control flow.
It is not generated by a UBE parser or VB6 compiler, does not establish UBE
compiler conformance, and does not freeze a production calling convention.

`SourceOracle.bas` and `source-oracles.json` state the matching UBE source
acceptance cases. The separate [native compiler gate](../native-compilation/README.md)
now compiles them through the VB6 bootstrap and executes all eight checks at
O0 and O2 using volatile runtime input. This hand-authored target gate still
neither parses nor executes that UBE file; its evidence remains separate.

The fixture uses a fresh Boolean success status and a separate result slot
published only on success. A test-local error-number slot models sticky Err;
this experiment does not implement the full Err object or thread-local storage.
A volatile input drives the failing callee, so LLVM cannot replace the test
with an assumed compile-time constant failure. The post-Raise source statements
are modeled on the nonfailure continuation, with no edge to them from Raise.

## Assertions

The executable returns zero only when every assertion passes. Nonzero exits
are bit masks with these meanings:

| Bit | Assertion |
|---|---|
| 1 | Success returning zero is usable and preserves an older Err 5. |
| 2 | Raise returns FAIL, sets Err 5, preserves unpublished result storage and never executes following code. |
| 4 | Default failure skips the remaining operand and assignment; the next statement sees the original destination 25. |
| 8 | An enabled caller handler receives the failure instead of normal continuation. |
| 16 | A failing call inside an active handler does not re-enter or propagate; its assignment is skipped and the handler continues. |
| 32 | Explicit cleanup before Raise occurs; cleanup after Raise does not. |
| 64 | A completed ByRef write remains visible after failure. |
| 128 | Two equal error numbers still produce two fresh failure statuses. |

Cleanup uses observable markers, not real OS resources. No resource-cleanup,
GC, stack-exhaustion, concurrency, cancellation or foreign-entry guarantee is
established by these markers. No native exception mechanism is used.

The runner checks each output's PE signature and x64 machine code, then asserts
the exact process exit at O0 and O2. Children have a 30-second timeout and
file-backed diagnostics. Two O2 negative controls deliberately return false
success and commit a failed assignment; exact nonzero masks prove that these
faults are rejected, rather than merely accepting a process that launches.

## Run

```powershell
rtk proxy powershell -NoProfile -File bootstrap/tests/failure-flow/check.ps1
```

The runner requires the already installed Clang 23.1.3 and its LLD linker. It
downloads nothing, runs no VB6 process and changes no registry settings.
Artifacts are kept in a uniquely named temporary directory printed by the
runner. Production compiler source-to-output acceptance uses the separate gate.

## Recorded evidence — 2026-11-10

The command above passed using installed Clang 23.1.3 and LLD in the normal
execution sandbox. Both O0 and O2 produced PE x64 outputs returning exactly 0
for all eight assertions. O2 negative controls returned exactly 158 for false
success and 4 for committing a failed assignment. The first runner attempt
exposed a fast-process ExitCode retrieval issue; retaining the process handle
before the bounded wait fixed the runner, and the complete gate then passed.
