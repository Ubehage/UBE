Check source and projects

Partially implementedFresh Compiler v3 - Windows x86-64 development tool

The fresh Compiler v3 reads native source and a bounded project format, then checks the supported declarations, names, types and procedure bodies. A successful check covers the bounded subset below; it does not generate or run an executable.

Prerequisites

Use bootstrap/out/v3/ube.exe only after the repository's current source CLI qualification and local replay have installed that exact executable. A retained binary from an earlier checkout may still report the old syntax-only boundary. This manual does not provide a standalone compiler installation. Contributor build prerequisites and qualification procedures are maintained in bootstrap/README.md and compiler/UBE_Compiler_v3/tools/. The historical bootstrap/build.ps1 route selects archived compiler source; it does not build the fresh v3.

Commands

./bootstrap/out/v3/ube.exe --check path/to/Main.bas
./bootstrap/out/v3/ube.exe --check path/to/App.UBE
./bootstrap/out/v3/ube.exe --check path/to/App.UBE --jobs 4

Run these commands from the repository root in PowerShell. Quote paths containing spaces. Relative invocation paths use the working directory captured at the start of the request. Options use the exact spelling and order shown.

--jobs is available only for project input. The default is one worker. Its value must be ASCII decimal digits with a numeric value from 1 through 4; leading zeroes are accepted. Signs, missing values, repeated options and additional options are usage errors. Worker count does not change which source failure is reported first.

Current project subset

The root manifest must have Kind = "Exe", Startup = "Main", a name and at least one source. It may explicitly reference one direct source library whose manifest name is UBECore and whose kind is Library. No library is found implicitly. Source processing follows root manifest order, then reference manifest order.

Native MODULE source has the qualified parser subset. Full grammar, conditional branch selection, other source kinds and designer input remain incomplete. Other libraries, transitive references, groups, resources, compiled libraries and startup forms are outside this project consumer. A valid unsupported facility is reported as unavailable; that does not make it invalid UBE.

Current semantic subset

Checking covers Boolean, Byte, Integer, Long and LongLong variables and constants; supported Sub and Function declarations; explicit types and visibility; names and calls across the admitted modules and direct reference; compatible assignments and parameters; and the executable's required parameterless Sub Main() or Function Main() As Long. It checks all declarations and bodies, including unused ones and the admitted reference's bodies.

Supported expressions include decimal integers, Boolean values, selected checked integer arithmetic and comparisons, Boolean and bitwise operators. Literal-only integer arithmetic is reduced during checking, and provable overflow or division by zero is rejected. Supported statements include ordinary assignments, calls, If/ElseIf/Else, While and matching Exit statements. Positional, named, optional and omitted scalar arguments, exact ByRef storage and individually parenthesized ByRef temporaries are covered. Selected opaque native types backed by Byte, Integer or Long and their explicit Value.Pack/Value.Unpack declarations are also checked.

Arrays, field records, String and the other scalar/object types, classes, properties, general intrinsics, Print, other control flow and many other full-language facilities remain unavailable. An unsupported declaration or body prevents success even when unused. The complete production UBECore and compiler sources exceed this subset: merely accepting their project or syntax does not validate them. Optimization and DebugInformation remain metadata; no program code is generated.

Results and exit codes

Exit codeMeaning today
0The entire input passed the bounded check. Standard output and standard error are empty.
1A source/project error, deferred facility, cancellation, resource limit or other failure prevented a complete check.
2Invalid invocation or command-argument transport failure.

No output program is created. A successful check also creates no intermediate or sidecar files. Exit zero means semantic acceptance of this supported subset, not complete UBE 1.0 support or successful runtime execution.

An ordinary semantic diagnostic identifies a fault in supported code, such as an undeclared name or a constant outside its selected integer range. A deferred diagnostic, such as UBE1433: datatype semantics are not implemented, identifies an implementation limit and does not declare the full-language construct invalid. Earlier input and syntax diagnostics retain their meanings. UBE1012 documents the historical syntax-only boundary.

Paths and limits

Source paths must remain within their manifest's lexical directory tree. Relative references may reach a sibling library. Containment is lexical: junctions and symbolic links can reach outside that tree. Opened-file identities detect aliases and duplicates within the qualified policy; the checker does not promise a filesystem snapshot.

Current request ceilings are 1 MiB per manifest, two packages, 256 sources, 16 MiB per source, 64 MiB total source bytes, 4 MiB total declared/resolved path bytes, and 8 MiB retained manifest/path/name bytes. Counted UTF-8 paths are limited to 131,068 bytes and the maintained Windows adapter's UTF-16 bound. These are development resource limits, not language limits.

Diagnostics

Project errors identify the owning input, original one-based line and Unicode-scalar column, and zero-based byte offset. Parallel source failures are selected in canonical source order. A filename is quoted and control characters are escaped. Error codes and exact messages are scoped to the compiler that emitted them; preserved v2 diagnostics are not a fresh-v3 catalog.

Read the complete specified project format separately from this implemented subset.
