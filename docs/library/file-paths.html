Counted-byte files and paths

Partially implementedBounded Windows native file-I/O gate qualified

Read uninterpreted file bytes and resolve strict UTF-8 paths without using zero-terminated source text. File tokens have explicit ownership and must be closed.

The current Windows native file-I/O gate passed 56 cases, including O0/O2 execution and injected failures. Qualification covers the bounded operations below, not native concurrency or the complete file/path library. Declarations on this page are reference examples, not a claim that each snippet ran verbatim.

File declarations

Function TryOpenByteFile(ByRef PathUtf8() As Byte, ByVal MaximumBytes As Long, ByRef Token As Long, ByRef Length As Long, ByRef Failure As Long) As Boolean
Function TryReadByteFile(ByVal Token As Long, ByRef Destination() As Byte, ByVal Start As Long, ByVal Count As Long, ByRef ReadCount As Long, ByRef Failure As Long) As Boolean
Function TryCloseByteFile(ByRef Token As Long, ByRef Failure As Long) As Boolean

Start with Token = 0 and nonnegative MaximumBytes. Open checks the regular disk file's size before publishing a positive token and Long length. Read borrows destination storage. Count must be nonnegative, at most 65,536 and fit the complete destination span; current arrays admit only 4,096 bytes. Start is a zero-based payload offset, independent of the array's language lower bound. A positive short read is progress; zero bytes means EOF. Failure preserves all destination bytes and returns ReadCount = 0. Zero count validates the token and range without an OS read.

File contents remain uninterpreted bytes. Paths are strict counted UTF-8 without embedded zero, case folding or Unicode normalization. Command-argument helpers are outside this increment.

Close explicitly

Copying a token does not duplicate its resource. Close after success, failure and cancellation. Closing zero succeeds. If close genuinely fails, the token remains owned for retry. Failed opening or creation cleanup can also return an owned nonzero token despite False; retain it and retry close. Neither garbage collection nor leaving scope closes the file.

Counted output

Function TryCreateByteFile(ByRef PathUtf8() As Byte, ByRef Token As Long, ByRef Failure As Long) As Boolean
Function TryWriteByteFile(ByVal Token As Long, ByRef Source() As Byte, ByVal Start As Long, ByVal Count As Long, ByRef WrittenCount As Long, ByRef Failure As Long) As Boolean
Function TryFlushByteFile(ByVal Token As Long, ByRef Failure As Long) As Boolean

The roles are File.TryCreateNew, File.TryWrite and File.TryFlush. Create requires Token zero and creates a new regular file exclusively. An existing path fails without truncation or modification. Create returns a writable token; Open returns a read-only token. Wrong access modes fail before I/O. Procedure spelling is arbitrary; exact Intrinsic declarations and role attributes select these operations.

Keep the source array unchanged for the write call. Each positive-count write performs one OS write and reports confirmed progress. The count ceiling is 65,536, further restricted by the current 4,096-element array limit and the complete source span. Positive short writes require another call with the remaining suffix. Zero progress must not cause an infinite retry loop. Zero count validates ownership and range without writing. Failure may leave a partially written newly created file; it does not roll back or delete it. Source bytes remain unchanged.

Write failure uses Failure = 15, flush failure uses Failure = 16, and both set Err = 57. Flush does not close a file or promise atomic publication, replacement or power-loss durability. The caller still owns cleanup. Ordinary file creation does not replace the compiler's guarded executable-publication path.

Path and ownership limits

Current paths are limited to 4,096 UTF-8 bytes. The Windows target uses wide file APIs. Path-normalization, file-identity and command-argument helpers from the archived implementation are outside this increment; they are not current qualified APIs.

Tokens belong to one execution context, are never native addresses and are never reused. At most 64 owners may be live in one context. Context disposal does not silently close user files. Preserve a primary failure through cleanup and retain any token whose close failed. A changing input file is not an atomic filesystem snapshot.

Status, errors and lifetime

Use each fresh Boolean and Failure, not stale Err. Success sets Failure zero and preserves incoming Err. A False file status does not itself raise language FAIL or enter an On Error handler. An ordinary wrapper may explicitly raise after completing cleanup. Error.Set(ByVal Number As Long) As Boolean records a positive error number and returns False without control transfer; a nonpositive number records Err 5.

Scalar output addresses must be distinct and must not overlap array storage used by the operation. Aliases are rejected before any output changes, so an invalid call cannot overwrite a live token while reporting its failure.
