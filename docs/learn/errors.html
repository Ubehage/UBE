Errors and Err

SpecifiedImplementation pendingUBE 1.0

A recoverable runtime failure records the current thread's error and abandons the failed statement. It does not automatically show a dialog or stop the program.

Default continuation

The default behaves like On Error Resume Next: skip the remainder of the failed statement and continue with the next one. A failed call supplies no usable value. FAIL describes that call outcome; it is not a source keyword, a string, zero, False, or Nothing.

This example reads text at runtime, so whether conversion succeeds depends on the program's command line:

Sub Main()
    Dim Count As Long
    Dim InputText As String
    InputText = Command$()
    Count = 25
    Count = CLng(InputText) + 10
    Print Count
End Sub

If InputText cannot convert to Long, Count remains 25 and Print executes. The addition is not performed. No zero is substituted to make Count become 10. If the input is "12", the assignment succeeds and Count becomes 22. These are specified outcomes, not executed compiler test results.

Already completed side effects remain. Skipping a statement does not undo earlier procedure calls, output, or writes through ByRef arguments. A failed declaration initializer leaves its already established variable at its neutral initial value.

Failed conditions

If an If or ElseIf condition fails, default execution skips the entire conditional, including its Else branch. If a Do or Loop condition fails, execution continues after the loop. This applies to While and Until, before or after the body. FAIL is neither True nor False. An enabled error handler still receives control; an already active handler skips the construct without recursive entry.

A failed ordinary statement inside a loop body skips only that statement. Earlier iterations and completed side effects remain completed.

Raise an error from a procedure

Function RequirePositive(ByVal Value As Long) As Long
    If Value <= 0 Then
        ' Release any resources this procedure owns before raising.
        Err.Raise 5
    End If
    RequirePositive = Value
End Function

When Err.Raise executes, it records the error, immediately exits this Function, and returns FAIL to the caller. It does not run the raising procedure's own handler instead. No statement after the raise executes on that path, and a previously assigned Function result is not returned as success.

The procedure must close its own files, release native handles and manually acquired locks, and perform any other required application cleanup before raising. The caller does not do this automatically. Compiler-managed stack, roots, temporaries and structured SyncLock exits still end safely; that does not close user-owned resources.

Handle a failed call

Each procedure invocation starts with default statement skipping, including every recursive call. A called procedure neither inherits nor changes its caller's handler. Handler mode, active-handler state and saved Resume state belong to that invocation and end when it returns. A returned FAIL is then handled by the caller's own current mode. Err is separate: returning does not clear the thread's recorded error.

Sub Main()
    Dim Count As Long
    On Error GoTo Failed
    Count = RequirePositive(CLng(Command$()))
    Print Count
    Exit Sub
Failed:
    Print Err.Number
    Err.Clear
End Sub

With RequirePositive declared as above, valid positive input prints its value. A conversion failure or a FAIL returned by RequirePositive enters the caller's Failed handler before the assignment completes. These examples illustrate specified behavior; runtime implementation is pending.

On Error GoTo 0 disables the label handler and restores default statement skipping. Explicit On Error Resume Next selects that default behavior. Neither changes the recorded error.

If a call fails while a handler is already running, the failed statement is skipped and execution continues within that handler. It does not recursively re-enter the handler or automatically propagate out of the procedure. The new error still replaces Err. An explicit Err.Raise executed by the handler itself still immediately exits its procedure.

Err remembers the last error

Successful operations preserve all previous error information. Err holds the last error until Err.Clear, a valid Resume, or a new error. A new error replaces the complete record; omitted fields use their neutral or defined default values. Returning from a procedure and changing handler mode do not clear Err. Each thread has its own error state.

An old nonzero Err.Number does not mean a later call failed. UBE uses the fresh call outcome for control flow. When manually inspecting Err, clear it before the operation if you need to distinguish a newly recorded error, or use the operation's explicitly documented fresh status.

A Try-style API may explicitly report validation failure, timeout, cancellation or another ordinary non-success through a returned status. That contract is separate from a raised language failure; the name Try alone does not decide its behavior.

Resume and limits

Valid Resume, Resume Next and Resume label leave an active handler and clear Err. Default skipping and On Error Resume Next retain the error. For a failed If or Do condition, Resume retries the condition and Resume Next continues after the complete construct. Retrying a post-test condition does not repeat the body first. These Resume forms remain specified, outside the current bootstrap subset. Boundaries for For, Select Case and SyncLock remain under definition.

Provably invalid operations are compile-time errors. A safely refused call due to insufficient stack records error 28 and returns FAIL without entering the callee. When safe continuation or reporting is impossible, UBE follows a controlled fatal-failure path rather than executing with corrupt state.

If a fresh FAIL escapes a worker's entry procedure, the worker ends normally. A ThreadWait observing that completion reports fresh FAIL in the waiting thread and records the captured error number there. Repeated waits and multiple waiters each receive that outcome through their own handler or default statement-skipping rules. Normal worker return with stale Err remains successful; timeout/cancellation returns zero and preserves Err.

The Error statement's equivalence to Err.Raise, complete Err member signatures, and error delivery across callback, startup and foreign boundaries still need their detailed contracts. Their presence in the language is not evidence of an implemented runtime.
